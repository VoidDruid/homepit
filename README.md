# Cockpit Service

Python-сервис для домашнего кокпита. Архитектура описана в [плане проекта](info/OVERVIEW.md).
Текущий прототип соединяет Launchpad MK2 с X4 через собственный Lua-мод и Windows Named Pipe.

## Структура

```text
cockpit/
  service.py                Независимое от игры ядро
  model.py                  Общие события и координаты панели
  adapters/x4.py            Телеметрия и команды X4, сервер Named Pipe
  devices/launchpad_mk2.py   MIDI-ввод и RGB через Mido/RtMidi
mods/x4py/                  Игровой мод, исходники редактируются здесь
scripts/link-x4-mod.ps1     Подключение мода к установленной X4
tests/                      Проверки ядра, реального pipe и Lua с подставным API
```

HOTAS подключается непосредственно к игре. Будущие игровые адаптеры и тактильная отдача добавляются отдельно от драйвера Launchpad.

## Python и MIDI

Используется **Python 3.12 x64, Mido + python-rtmidi**. Mido отвечает за сообщения и порты; RtMidi — за MIDI-ввод/вывод. Протокол MK2, назначение кнопок и RGB остаются в нашем небольшом драйвере. [Рекомендуемый backend Mido](https://mido.readthedocs.io/en/stable/backends/rtmidi.html).

Для `python-rtmidi 1.5.8` опубликован Windows x64 wheel под CPython 3.12. В проверенной поставке wheel для 3.13 отсутствует, а сборка исходников требует C++-компилятора. [Файлы пакета](https://pypi.org/project/python-rtmidi/#files).

На этой машине Python 3.12.16 установлен локально в `.python`, рабочее окружение — `.venv`.
Версия Python ограничена в `pyproject.toml`, зависимости закреплены в `uv.lock`.
`uv sync` устанавливает только зависимости. Сервис запускается прямо из исходников командой `python -m cockpit`; сборка и установка самого проекта отключены (`tool.uv.package = false`).

Воспроизведение окружения из корня проекта (PowerShell, установлен `uv`):

```powershell
uv sync --python 3.12 --extra test --locked
```

## Запуск

Из корня проекта:

```powershell
# Список MIDI-портов
.\.venv\Scripts\python.exe -m cockpit --list-midi

# Настоящее подключение к X4 и Launchpad
.\.venv\Scripts\python.exe -m cockpit

# Диагностика X4 без открытия MIDI-портов
.\.venv\Scripts\python.exe -m cockpit --no-device
```

`Ctrl+C` останавливает сервис и освобождает порты. При штатном выходе LEDs гаснут.
При нескольких MK2 нужно указать точные имена через `--midi-in` и `--midi-out`, взяв их из `--list-midi`.
После отключения/подключения USB перезапустить сервис; автоматическое восстановление MIDI пока не реализовано.

Раскладка Session, квадратные кнопки:

| Кнопка | Назначение |
|---|---|
| Верхняя левая, MIDI 81 | Зелёный — свежая телеметрия; красный — связи нет или данные старше 3 секунд |
| Справа от неё, MIDI 82 | Янтарный — игра сообщает о паузе |
| Нижняя левая, MIDI 11 | Нажатие отправляет `ping`; синий — готовность, янтарный — ожидание, зелёный — получен ответ, красный — ошибка |

Ожидание ответа — 2 секунды; результат показывается одну секунду. Повторное нажатие во время ожидания и удержание кнопки не создают новых запросов. Ответ с чужим или просроченным ID игнорируется. После разрыва команды не повторяются.

`--no-device` показывает в консоли изменения состояния панели и соединения; запросы с физической кнопки в этом режиме недоступны. Демонстрационный режим не реализован.

## Мод X4 и обновление исходников

Создана Windows junction:

```text
G:\SteamLibrary\steamapps\common\X4 Foundations\extensions\x4py
  → C:\Проекты\cockpit\mods\x4py
```

Для повторного подключения или другой установки игры:

```powershell
.\scripts\link-x4-mod.ps1 -GamePath 'G:\SteamLibrary\steamapps\common\X4 Foundations'
```

Скрипт не перезаписывает существующий каталог и повторно запускать его безопасно.
Junction сразу отражает изменения файлов, но **не перезагружает код в памяти игры**.
Для надёжного применения изменений мода перезапустить X4. Для правок только Lua можно отдельно проверять `/reloadui`; изменения XML и зависимостей требуют перезапуска.
Правки Python применяются после перезапуска сервиса.

Зависимости:

1. В X4 должны быть включены **SirNukes Mod Support APIs ≥ 1.95** и **Cockpit x4py**. Мод использует Steam ID уже установленного SirNukes.
2. Для Named Pipes установить **Protected UI Mode = OFF** и перезапустить игру. Сервис эту настройку сам не изменяет.

С UI Extensions and HUD переключение Protected UI Mode может оставить только фон меню, а после принудительного выхода настройка не сохранится. Проверенный 11.11.2026 порядок: выключить UI Extensions and HUD, штатно выйти и перезапустить X4; выключить Protected UI Mode, штатно выйти и перезапустить; убедиться, что осталось OFF, включить UI Extensions and HUD обратно и снова перезапустить. Все эти действия выполнять из главного меню, затем загружать сохранение.

Отдельные x4-simpit, X4_Python_Pipe_Server, Native Hotkey API и Simple Hotkeys для этого прототипа не нужны. Cockpit Service сам создаёт сервер, SirNukes в игре подключается к нему как клиент. [Named Pipes API](https://github.com/bvbohnen/x4-projects/blob/master/extensions/sn_mod_support_apis/documentation/Named_Pipes_API.md).

## Ручная проверка в X4

Из PowerShell запустить **один** экземпляр сервиса, оставив консоль открытой:

```powershell
Set-Location 'C:\Проекты\cockpit'
.\.venv\Scripts\python.exe -m cockpit
```

1. До загрузки игры верхняя левая и нижняя левая квадратные кнопки должны быть красными. Это нормальное ожидание соединения.
2. Загрузить тестовую игру/сохранение. В главном меню мост не запускается. После загрузки верхняя левая кнопка должна стать зелёной, нижняя левая — синей. В консоли появится `X4 pipe connected`.
3. Нажать и отпустить нижнюю левую кнопку. Она должна стать зелёной примерно на секунду, затем снова синей. Янтарное ожидание может быть слишком коротким, чтобы его заметить. В консоли должны появиться `ping` и `pong` с одинаковым ID. Удержание кнопки должно отправить только один запрос.
4. Включить игровую паузу штатной клавишей. Вторая квадратная кнопка верхнего ряда должна стать янтарной в пределах примерно секунды; после снятия паузы — погаснуть. Связь должна оставаться зелёной. Повторить `ping` во время паузы.
5. Остановить сервис через `Ctrl+C`: подсветка должна погаснуть. Запустить снова при открытой игре: связь и `ping` должны восстановиться без перезапуска X4.
6. Оставить сервис включённым и полностью закрыть X4: индикатор связи должен стать красным, индикатор паузы погаснуть. Запустить X4 и загрузить игру повторно — соединение должно восстановиться.
7. После успешного основного теста отдельно выполнить `/reloadui` в игровом чате, если эта команда доступна в текущем режиме игры. Проверить восстановление связи и ровно один `pong` на нажатие. Перезапуск X4 остаётся основным способом применения изменений мода.

Если тест не прошёл, записать номер шага, цвета трёх кнопок и последние строки консоли. При необходимости повторить запуск с `--no-device`: это отделит проблемы игрового соединения от MIDI. Для диагностики Lua добавить в параметры запуска X4 `-debug all -logfile cockpit-debug.log`; строки нашего мода имеют префикс `[x4py]`. Не считать успешным ответ от подставного клиента: в ручном тесте `pong` должен прийти именно из работающей X4.

## Текущие возможности и проверка

Реализованы диагностическая команда `ping/pong`, телеметрия паузы раз в секунду, RGB-индикация, тайм-ауты и восстановление игрового pipe. Управление полётом, щит/корпус и тактильная отдача ещё не реализованы.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

На 10.11.2026 проходят 18 автоматических тестов: ядро, реальный Windows pipe с тестовым клиентом, Lua 5.1 с подставными игровыми API и MIDI-драйвер с подставными портами. Проверены оба порядка запуска, гонка подключения, переподключение, отмена ожидающего чтения, неверные сообщения, пауза и защита от повторных запросов. RtMidi видит вход `Launchpad MK2 3 0` и выход `Launchpad MK2 3 1`.

11.11.2026 подтверждён живой тест в X4 9 после отключения Protected UI Mode: пользователь наблюдал изменение подсветки и успешное нажатие ping/pong. В логе сервиса зарегистрированы подключение, смена состояния паузы туда и обратно, а также `ping` и `pong` с одинаковым ID. Для этого запроса интервал между строками отправки и ответа составил около 41 мс; игровой лог также содержит соответствующий `pong`. Базовый цикл Launchpad → Python → X4 → Python → RGB работает.

11.11.2026 также подтверждён ping во время паузы (ответ в логе примерно через 21 мс). При первом перезапуске игры выявлена и исправлена ошибка: SirNukes отправляет служебное сообщение `garbage_collected`, которое сервис раньше считал нарушением протокола и завершался. Теперь сообщение переводит соединение в ожидание нового клиента; серверный handle переиспользуется, поскольку SirNukes может оставить старый клиентский handle открытым. Регрессионный тест проверяет переподключение и отсутствие повторной отправки старых команд; всего проходят 19 автоматических тестов.

Повторный живой тест перезапуска игры 11.11.2026 прошёл: сервис обработал освобождение Lua pipe, дождался новой загрузки и снова получил телеметрию и ответы pong. Пользователь подтвердил работу Launchpad после перезапуска. Также подтверждён запуск исправленного сервиса при уже загруженной игре. Штатная остановка через Ctrl+C с повторным запуском и `/reloadui` остаются в ручном сценарии выше.

## Протокол диагностического моста v1

Канал `\\.\pipe\cockpit_x4py_v1`, duplex, message mode, только локальные клиенты. Каждая запись — одно ASCII-сообщение, без перевода строки и NUL, не более 1024 байт:

| Направление | Сообщение |
|---|---|
| Игра → сервис | `x4py/1 state 0` / `x4py/1 state 1` — пауза выключена/включена |
| Сервис → игра | `x4py/1 ping <id>` |
| Игра → сервис | `x4py/1 pong <id>` |

`id` — 32 строчные шестнадцатеричные цифры. Ответ подтверждает только соответствующий запрос. Это небольшой диагностический протокол; добавление игровых действий потребует явных обработчиков команд, результатов и расширения схемы телеметрии. Выполнение произвольного Lua/Python не предусмотрено.

Отдельно от сообщений x4py адаптер принимает точное служебное сообщение SirNukes `garbage_collected`: оно завершает текущий сеанс и разрешает новое подключение. Остальные неизвестные сообщения остаются ошибкой протокола.

Игра пытается подключиться раз в секунду и передаёт текущее состояние паузы раз в секунду по реальному времени. Python использует overlapped I/O без блокирующего ожидания в основном цикле; одновременно допускается одна запись команды. Некорректные сообщения завершают Python-сервис с ошибкой, а в Lua отключают мост до перезагрузки с записью в debug log. Обычный разрыв pipe восстанавливается автоматически.
